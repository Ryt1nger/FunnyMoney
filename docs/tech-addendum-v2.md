## Часть 2. Что поправить (и почему)

### 2.1. «Native оболочка» — формулировка неверная
Capacitor — не нативная оболочка, а нативный контейнер с WebView внутри. Кроссплатформу
заказчик разрешает (п. 3.2), но называть это «Native» нельзя — на защите эксперт спросит.

Правильно: `Android APK (Capacitor) → WebView → React UI → Game Core → Local Storage`.

### 2.2. SQLite для MVP избыточен
Простыми словами: база нужна, когда записей много и по ним надо искать. У нас один игрок,
один питомец, один кошелёк — это одна тетрадка, ради неё не заводят картотеку. SQLite добавит
зависимость, отладку под Android и риск сломать сборку перед сдачей.

Правильно: **Capacitor Preferences** (нативное хранилище) или файл — ТЗ разрешает
«файловое хранилище или эквивалент». SQLite оставляем как план развития.

### 2.3. Критично: localStorage нельзя как основное хранилище
Сейчас прогресс лежит в localStorage. Это карман внутри браузера, и Android вправе его
почистить при нехватке места — ребёнок откроет приложение, а питомца нет. По п. 2.5.13
прогресс обязан переживать перезапуск, это проверяется в демонстрации (Приложение А, шаг 11).

Правильно: писать в Capacitor Preferences, localStorage — только fallback для веб-версии.

### 2.4. Splash нужен двухуровневый
Пока грузится WebView, React ещё не существует и рисовать Мишку некому — между запуском
и Мишкой мелькнёт белый кадр. Нужно: нативный splash Capacitor (мгновенно) → фирменный
экран загрузки на React → главный экран; нативный splash скрывать вручную после первого кадра.

### 2.5. Демо-режим: важна не скорость, а отсутствие ожидания
ТЗ требует, чтобы обязательные шаги шли подряд без привязки к календарю и чтобы тестовый
профиль сбрасывался к исходному состоянию. Значит: кнопка «следующий период» + кнопка сброса.

### 2.6. Приоритеты нужно переставить — главное замечание
В прототипе есть питомец, магазин и уроки. Но ядро задачи заказчика — **план бюджета → факт →
сравнение**, финансовая цель и накопления (критерий 8.3: три самостоятельные, но связанные
механики). Этих механик у нас нет вообще, без них решение не соответствует задаче.

Новый порядок:
1. Стабильный запуск APK на физическом устройстве
2. Offline + надёжное локальное сохранение
3. План бюджета (обязательное / необязательное / накопления) и сравнение план↔факт
4. Финансовая цель и накопления
5. Покупки с последствиями для состояния питомца
6. Задания (мин. 6 по 3 темам)
7. Стадии развития питомца (мин. 3)
8. Раздел для взрослого
9. Демонстрационный режим и сброс профиля
10. Анимации и визуальные эффекты

## Часть 3. Чего не хватало (по этому оценивают)

**Устройство и отклик:** Android 8.0+, портрет, экраны от 360 dp (п. 3.1.1–3.1.2); проверка на
физическом устройстве с ОЗУ от 3 ГБ, не только эмулятор (п. 3.1.3); отклик на действие
не более 1 секунды (п. 3.4) — пункта не было совсем.

**Сборка и RuStore (п. 3.3):** подписанный релизный APK, ставится без среды разработки;
уникальный package name, версия и номер сборки в документации; черновик карточки RuStore —
название, категория, описания, иконка 512×512, ≥3 скриншота, обоснование возрастной маркировки;
права на все изображения, шрифты, звуки и библиотеки (наши ассеты сгенерированы ИИ — указать прямо).

**Разрешения и секреты (п. 3.4, 3.1.4):** только необходимые разрешения с обоснованием каждого;
камера, микрофон, геолокация, контакты, Bluetooth не нужны; в репозитории нет паролей, токенов
и ключей подписи.

**Тесты (п. 3.4, критерий 8.2):** логика бюджета, списаний, накоплений и прогресса покрывается
автотестами либо описанным набором тест-кейсов. Ручной проверки недостаточно.

**Доступность и UX (п. 3.6) — отдельный критерий:** тач-зоны ≥48×48 dp; текст ≥16 sp и читаемость
при системном увеличении шрифта; цвет не единственный способ показать ошибку/успех/категорию;
звуки и анимации отключаемы; действия, меняющие прогресс, требуют подтверждения.

**Безопасность и защита ребёнка (п. 3.5):** без аккаунта и сбора персональных данных; нет рекламы,
подписок, внутриигровых покупок, случайных платных наград и внешних ссылок; тексты не пугают и
не стыдят; взрослый может сбросить и удалить данные сам.

**Раздел для взрослого (п. 2.5.12):** обязателен, за простым барьером (удержание кнопки или
арифметический пример); внутри — цели, пройденные темы, общий прогресс, без негативных оценок ребёнка.

**Минимальный объём контента (п. 2.6):** 9 комбинаций внешности питомца; 5 игровых периодов подряд
в демо-режиме; 6 заданий по 3 темам; 8 позиций покупок обоих типов; 3 цели накопления;
3 стадии развития питомца.

**Документация (раздел 5) — 12 обязательных пунктов:** README, инструкция сборки APK, архитектура,
структура данных, матрица соответствия требованиям, формулы расчёта, карта образовательного
контента, обоснование UX и доступности, описание разрешений, тест-кейсы и отчёт о проверке на
устройстве, известные ограничения, перечень библиотек и лицензий.

## Часть 4. Итоговый стек

```
Android APK (Capacitor)
  └── WebView
        └── React + TypeScript + Vite (UI)
              └── Game Core (экономика, бюджет, цели, состояние питомца) — чистые функции, без UI
                    └── Storage Adapter
                          ├── Capacitor Preferences (основное, нативное)
                          └── localStorage (fallback для веба)
Учебный контент (уроки, задания, товары) — отдельными файлами данных
Backend — отсутствует в MVP
```

Требование «учебный контент отделён от интерфейсного кода» (п. 3.2) уже выполняется:
сценарии, уроки и товары лежат в `src/data/`.
